# Configuration

The plugin's form is enough for one provider; this page is `install.sh` in detail and the setup by hand.

## install.sh

`./install.sh` needs no checkout, so it also runs as `curl -fsSL https://raw.githubusercontent.com/asx8678/dsk/main/install.sh | sh`, and running it again updates dsk. `--local` installs this checkout as dsk@asx8678: Claude Code loads it from the checkout, so edits take effect in the sessions started afterwards, and rerunning `--local` refreshes the copy that the `dsk` command of your own shell runs. A run that is going is not disturbed by an install or an update: it starts its scripts from the real path of its own file, found once when it starts, and `~/.local/bin/dsk` is replaced in one step. After `--dev` or `--local` the runs use the checkout itself, so an edit to `skill/scripts/dsk.py` reaches a running session at its next turn. Either id asks for the provider in the same way: `/plugin configure dsk@asx8678`, or `dsk@skills-dir` after `--dev`. Everything below is optional: it is how to set dsk up by hand, with more than one provider. What a config file and the key file say wins over the plugin's form.

## By hand

1. **Keys.** `dsk` takes each key from the environment, or else from `~/.config/dsk/env`, a private file (mode 600) of lines like `export DEEPSEEK_API_KEY='...'`. Nothing has to be sourced, so Claude Code needs no setup. A key read from the file never enters `dsk`'s environment, so scripts, `sh()` and checks cannot see it.
2. **Config.** `~/.config/dsk/config.json` names the environment variables; it never holds a key.

   ```json
   {
     "route": ["thirdparty", "official"],
     "profiles": {
       "thirdparty": {"base_url": "https://example.com/v1", "key_env": "DSK_THIRDPARTY_API_KEY", "model": "deepseek-v4.1-flash", "compact_at": 24000, "extra": {}},
       "official":   {"base_url": "https://api.deepseek.com", "key_env": "DEEPSEEK_API_KEY", "model": "deepseek-flash", "compact_at": 48000, "extra": {}}
     },
     "search": {"base_url": "https://api.deepseek.com", "key_env": "DEEPSEEK_API_KEY"},
     "sh_deny": ["terraform apply", "kubectl delete", "pip install", "npm install"],
     "env_pass": []
   }
   ```

   The `official` profile, the `search` block and a default `sh_deny` list are built in, so the file may hold only what differs. `extra` is merged into the request body; a `null` value removes a key the provider rejects. Optional keys: `effort` (`off`, `low`, `high` or `max`, default `off`: the thinking effort of a `dsk run` without `--effort`), `backoff` (retry waits in seconds, default `[2, 6, 18]`) and `limits` (`turn_seconds` 600, `run_seconds` 3600, `run_tokens` 2000000; `output_chars` 6000 and `read_chars` 24000, how many characters of what a turn printed go back to the worker, for a turn that only reads files and for any other; `idle_seconds` 90, how long a streamed reply may send nothing, `reply_seconds` 600, how long a whole reply may take, and `reviewer_seconds` 300, how long one independent review may take). `recheck` (default `false`) gives every write run the second look, and `reviewer` (default `false`) the independent reviewer, unless a run says `--no-recheck` or `--no-reviewer`; `reviewer_effort` (default `off`) is the reviewer's thinking effort, `reviewer_tokens` (default 4,000) caps its reply, reasoning included, and `reviewer_calls` (default 2) is how many reviews one round may have. See [Second look and reviewer](internals.md#second-look-and-reviewer). A profile may set `max_sessions`, the number of runs the provider serves at once (see [Providers](#providers)), and `price`, dollars per million tokens as `{"in": 0.005, "cached": 0.003, "out": 0.57}`, from which `status --json` reports each job's cost. `headers` adds request headers; in a value, `{session}` becomes an ID that stays the same for the whole run, across `answer`, `reject` and failover. OpenCode Go needs `"headers": {"x-opencode-session": "{session}"}`. `pause_hours` (default 1) is how long a profile is skipped after it reports its credit used up, when the error names no reset time (see [Providers](#providers)). `sandbox` is `auto` (the default: scripts and checks run under `sandbox-exec` where it works, and a report says `sandbox: off: why` where it does not), `off`, or `required` (a run that cannot have it fails at the start). `sandbox_write` lists more folders they may write, such as a build cache the defaults miss, and `sandbox_hide` more paths they may not read. `dsk run --no-sandbox` turns it off for one task, unless it is `required`.
3. **Check it.** `dsk doctor` tests each profile: the key, the model ID, that thinking-off is honoured, five replies over a three-turn exchange, and whether and where cached tokens are reported.
4. **Permissions.** The skill pre-approves `dsk` only for the turn that invokes it. For later turns and background runs, add `"Bash(dsk *)"` to `permissions.allow` in `~/.claude/settings.json`. That rule also covers every `--check` command and every shell command the worker runs: none of them reaches a permission prompt, and only the guards in [Guardrails, stated honestly](../README.md#guardrails-stated-honestly) stand in the way.
5. **Display.** In a session that was already open, run `/reload-plugins` once. `/dsk-jobs on` loads the live display and `/dsk-jobs off` unloads it; see [The plugin](plugin.md).

## Providers

A session starts on the first profile in `route`. With `"route_order": "fastest"` in the config, `dsk run` first puts the route in order of measured speed: `dsk bench` times each profile with two small requests (the quicker one counts; a profile whose slots are all taken keeps its last time) and keeps the result in `~/.local/state/dsk/speed.json`; a run measures again by itself when a profile's time is older than `bench_minutes` (default 15), and runs started together measure once. A full fast profile hands over to the next fastest, and a session that goes on stays on its profile, where its cache is. `dsk stats` shows the seconds per turn each profile really took. On 402, or when retries of a network failure, 408, 429 or any 5xx are used up, it continues on the next profile in a new series. A failure that took more than 30 seconds to arrive, such as a gateway's 524 after its own timeout, is not sent to the same profile again while another one can take over. A worker that sends the same reply three times in a row, or keeps alternating between the same two, is moved to the next profile as well, and the run stops as `stuck` only on the last one. A worker that only reads for twelve turns in a row in a run with `--allow` is told to start writing. The first line of a report names the profiles a session left, as in `zro after coralbricks`. A 400 whose message mentions a limit is treated as a 429, because one gateway reports its concurrency limit that way. A profile with `max_sessions` N has N slots, file locks in `~/.local/state/dsk/slots/`; a run holds one from its first request on that profile until its `dsk` process exits. Profiles that reach the same `base_url` with the same `key_env` share one set of slots, limited by the smallest `max_sessions` among them. When all are taken, the run moves to the next profile without sending a request, or, on the last profile in the route, waits for a slot; the display says nothing of such a skip, and shows a real failover as `↯ coralbricks 429 → opencode`. `dsk doctor` takes a slot too, and leaves a profile unchecked while running jobs hold all of its slots. An error that says the credit or quota is used up is not retried: a 402, or a 400, 403 or 429 whose message mentions quota, credit, balance, billing, payment, allowance or a usage limit, but not concurrency, "at a time" or a rate limit. The profile is then paused until the reset time the message names (if within a week), or for its `pause_hours`. Every run skips a paused profile without sending a request, except the last profile in the route, which is always tried. Pauses are files in `~/.local/state/dsk/paused/`; `dsk configure` shows them, and deleting one ends it. A reply with no `finish_reason` whose output reached `max_tokens` counts as cut off (`length`), because one gateway leaves the field empty.

Replies are streamed. A gateway that waits for a whole reply before it sends anything gives up after about 125 seconds with a 524; a stream sends data from the first second, so a long reply gets through. A stream that sends nothing for `idle_seconds` counts as a network failure, and so does one that ends with neither a `finish_reason` nor `[DONE]`: both are retried, or moved to the next profile like any other. A reply still going after `reply_seconds` is cut off there and handled as one that reached `max_tokens`. A provider that answers in JSON is read as before; `"extra": {"stream": false}` asks for that. `dsk doctor` says whether a profile streams, and `dsk stats` shows how long each profile took to send the first data of a reply. A failover keeps the conversation, so before the next profile is sent anything, the series is compacted if the last request was over that profile's `compact_at`.
