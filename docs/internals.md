# How dsk works

The protocol in full; the README has the short version.

## Reply format

Every request carries one static tool, `run_code(code)`, and with thinking off the call is forced. A reply that is not exactly one valid call is not run and gets a fixed message back, with one exception: in a read-only run, a reply of 400 characters or more of text with no call is taken as the worker's answer, as if it had called `done()` with it (all 34 such replies in the logs of 73 sessions were finished answers).

## Function API

Inside the script: `read`, `write`, `edit`, `glob`, `grep`, `sh`, `search`, `fetch`, `note`, `ask`, `done`. `write("@answer", text)` stores a long research answer in the session; `read("@3")` returns the full output of turn 3, and `read("@stdin")` an attachment that was piped in. A page fetched twice in one session is served from the session's copy. `"@scratch/name"` is a file in the session's scratch folder, which `sh()` and the checks know as `$DSK_SCRATCH`: the one place outside the working directory a script may write, for probes and other throwaway files. `read` also takes a path outside the working directory, since `sh()` can read it anyway; `write`, `edit`, `glob` and `grep` do not. It is never part of the change and is removed when the session is accepted or dropped. A script kept there resolves its imports from that folder, not from the project. `glob()` lists what git does not ignore; a pattern that names a folder, such as `shots/*.png`, also finds ignored files in it when nothing else matches.

## Execution

Each script runs in a fresh `python3 -I` child with a hard timeout that kills its process group. The allowed modules are already imported, and `import glob` gives the script dsk's own `glob()`. What a turn printed goes back cut to `limits.output_chars`, or to `limits.read_chars` when the turn only read files: in the logs of 118 sessions, nine in ten of the turns that were cut only read. A reply identical to the one before is not run and gets one warning; a second one stops the run as `stuck`, or moves it to the next profile when there is one. A script that is the previous one with only its numbers changed, changes no file and prints nothing the last four turns had not shown counts the same way, and three such replies in a row move or stop the run: one worker spent its last 15 turns printing ever shorter slices of the same lines. The request after such a reply is sent with temperature 0.7, and with 1.0 after two in a row, when thinking is off. Three logged loops of identical replies were sent to their provider again, four times each at each setting: the same script came back 11 times of 12 at temperature 0, twice at 0.7 and never at 1.0. A logged loop of near-copies came back 8 times of 8 at 0, once at 0.7 and twice at 1.0. A shell command that fails the same way three times in a row, with the same output, gets a note that the last changes did not touch what it tests. A reply cut off at the output limit is not kept in the conversation. A report for `stuck` or `limit` has a `spent:` line, the turns of the round by kind, and, when nothing was changed, `last:`, what the worker last printed.

- An AST gate refuses imports outside a fixed list of pure standard-library modules, `open`, `exec`, `eval`, `compile`, `__import__`, `input`, and any name starting with `__`. A script Python cannot parse at all, such as one with a lone surrogate, is refused the same way and costs a turn, not the run.
- The gate reads the script; an audit hook in the child sees what it then does. A script that opens a file for writing, changes or removes one, or starts a process by a road the gate cannot see (`io.FileIO`, an allowed module's own `os`) gets a `PermissionError` that names `write()`, `edit()` or `sh()`, before anything happens. The API's own functions are exempt while they run, and so is Python's bytecode cache. So a script that started no shell command has changed exactly the files it wrote with `write()` and `edit()`, which is what the scope gate takes for granted when it leaves every other change of that turn alone as someone else's.
- The ledger keeps 200 characters of a call's first argument; a path that `write()` or `edit()` was given is logged whole beside it when it is longer, since the scope gate tells what a script wrote from those records.
- The child reports every API call to the parent over a socket. Reports and compaction are built from that ledger, not from what the model says.
- `search` and `fetch` execute in the parent, which alone holds the key.
- Scripts, `sh()` and checks get a scrubbed environment: no key variables, nothing that looks like a credential, cloud CLIs pointed at empty configuration.
- On macOS the script's process, and with it every `sh()` command, and each check run under `sandbox-exec` with a profile built per session. Writes are denied, then allowed in `/tmp`, the temp folder and the build caches (`~/Library/Caches`, `~/.cache`, `~/.npm`, `~/go/pkg/mod`, Xcode's DerivedData, SwiftPM's folder, and `sandbox_write`), denied again under `/private/tmp/claude-*`, where other Claude sessions keep their scratchpads, and allowed in the working directory, the scratch folder and the session's answer file. Git's own directory is denied, all but its index, because hooks and config run code outside any sandbox. Reading dsk's key file, the plugin's `options.json` and the `.new` copy written beside it, `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.netrc`, `~/.config/gh`, `~/.docker`, `~/.kube`, the Keychains and `sandbox_hide` is denied. Whether the profile applies is tried once when the run starts and kept in the session's head; a command's output is never read to guess it, since `sandbox-exec` exits 65 on a bad profile and so may any command. A session started without a sandbox keeps running without one.
- `sh()` refuses `sudo`, any git command that writes, and the `sh_deny` list: by default `pip install`, `pip3 install`, `npm install`, `npm i`, `npm ci` and the terraform, kubectl and helm commands that change something. For the git check a quoted string is text, not a command, so `grep "git commit" docs` runs, while the script of `sh -c` or `eval` is still read; `sudo` and the deny list are matched on the whole command as before, quoted text included. Each command runs in its own process group, which is killed when the command returns. An out-of-scope path is restored by its name, never as a pattern: `src/[ab].txt` read as one also names `src/a.txt`.

## Cache discipline

The system prompt and the tool are constants in the source. The first user message is ordered stable-first: `DSK.md` (labelled as an attached file, so the worker knows it has it), run header, attached files, brief. A session is an append-only JSONL log, and every request is rebuilt from it. Before each send, `dsk` checks that the serialized messages extend the previous request of the series byte for byte, using a length and SHA-256 stored in the log, so the check also holds across `answer` and `reject`. Only session start, compaction and provider failover start a new series. Hit tokens are recorded per turn; `dsk show ID --log` prints them.

## Streaming

Every request asks for a stream with usage at the end (`stream_options.include_usage`). The reply is rebuilt from the events into the shape a JSON reply has: text, `reasoning_content` and `reasoning` each joined on its own, tool calls joined by index, the last `finish_reason`, the usage chunk. The socket timeout is `limits.idle_seconds`, so a stream that goes quiet fails like a dropped connection; `limits.reply_seconds` caps the whole reply. A response that is not `text/event-stream` is read as JSON. Each `usage` record has `first`, the seconds until the first data arrived.

## Attachments

`--file PATH` attaches a whole file and `--file PATH:A-B` lines A to B of it, under that name; the run header tells the worker how many characters a turn shows.

## Compaction

When the last request exceeds the profile's `compact_at`, the series restarts as: system prompt, first message with a digest in place of the dropped turns, then the last two turns verbatim. The first message keeps the task. In a round that a reject started, it also keeps that reject's defects, under `## The lead's review`. Attached files of up to 4,000 characters always stay. Larger ones stay in the order attached while the compacted messages fit in half of `compact_at`, counted at 3 characters a token. If any were dropped, one last message names them, a line range as `read("PATH", A, B)`, and tells the worker to read a file again before relying on it. The digest holds all notes, every question with its answer, one ledger line per action in the dropped turns, and the files changed so far. There is no model call, so the same log always compacts to the same bytes. The check runs again before every request, against the `compact_at` of the profile the request goes to, so a failover to a profile that compacts sooner compacts first. In a `--worktree` run, a dropped file that git ignores is named by its path in the main tree, since the worktree has no copy of it.

## Gates

Write mode (`--allow`) needs a git repository.

- *Snapshots:* the working tree is recorded as a tree object at start, around every script and check, and at every stop, in an index kept in the session directory, so your own index is untouched and only changed files are hashed again. Only what changes while a script or a check is running is attributed to the worker. Its change set is those files, from the start snapshot to the last stop, so it excludes your uncommitted changes and anything you edit between its turns.
- *Scope:* after every script and after the checks, what changed outside `--allow` during that script is undone by `dsk`, listed as `scope: reverted ...`, and reported to the worker. A copy of whatever is undone stays in the session directory. A script that started no shell command is charged only for the files it wrote, since `write` and `edit` are checked when called. A script that is interrupted or killed is still settled, by the same run or by the next command on the session.
- *One in-place run per tree:* a second run without `--worktree` is refused while the first is working, so one run never undoes another's work.
- *Checks:* `dsk` runs each `--check` itself. A failure goes back to the worker and the run continues. At a `stuck` or `limit` stop where the worker changed files, `dsk` runs the checks once more, so the report says whether the partial work passes them.
- *Research:* every URL in an answer must have been returned by `search()` or opened by `fetch()` in the session; others are listed as unverified.
- *Review:* the Stop hook (`dsk status --hook`) exits 2 while a session started by the current Claude Code session is in `review`.

## Worktrees

`--worktree` runs the task in a fresh git worktree seeded with your uncommitted state; the repository needs at least one commit. `accept` applies the worktree as it stands to the main tree with `git apply`: changes land uncommitted, a conflict is refused as a whole, and it waits for any in-place run in that tree. An edit you made in the worktree, between rounds or after the worker stopped, is included when its path matches `--allow`; one outside `--allow` is not applied, and is kept as `late.patch` in the session directory. In place, `reject --drop` reverse-applies the worker's diff and refuses if those files have moved. A worktree run that ends `done` changed nothing, so its worktree and branch are removed at once. A run that wrote a file git ignores with `write()` or `edit()`, and that file is still there, ends `review` instead, even when nothing tracked changed: the report names each such path on an `ignored:` line, and `accept` applies only the tracked diff before deleting the worktree, so they are not carried over.

## Continuing

`dsk continue ID "task"` sends a next task into a session that is `done` or `accepted`: the same conversation, so the worker keeps what it has read and the request still extends the cached prefix. It logs a `base` record with the round's own terms (`--allow`, `--check`, `--max-turns`, each kept from before when left out) and a new start snapshot, so the review packet, `accept` and `reject --drop` deal with that round's changes only. A worktree that `accept` or `done` removed is built again from the main tree as it is now, and the earlier round's `@answer` is kept aside as `answer.N` in the session directory. A session whose earlier round had no `--allow` gets at least 30 turns, the default of a writing run, when its first `--allow` arrives, unless `--max-turns` is given. After a compaction the worker's first message carries the current task and the terms of its round, and the digest lists the earlier tasks as finished. Every report has a measured `context:` line, the size of the next request against the profile's `compact_at`, with the number of compactions so far: it is what tells the lead to start a fresh run instead.

## Second look and reviewer

Both are off unless a run asks for them (`--recheck`, `--reviewer`) or the config turns them on. Each is a term of the round, stored with `--allow` and `--check`, so `continue` keeps it unless told otherwise.

**Second look.** When the first `done()` of a round passes its checks and the worker changed files, `dsk` does not stop. The turn's result goes back with a fixed text (`RECHECK`) and the diff of the change: check each requirement of the task, and each defect of the lead's review, with a normal and an edge input, question that check, then fix and call `done()`, or call `done()` again unchanged. The same script sent again is taken as final and not run twice: it ran and passed its checks a turn ago, and nothing has moved since. There is one second look per round. It is skipped when thinking is off, since it happens in the worker's reasoning, and when the round has no turn, time or tokens left, so a hand-in that passed never ends as `limit` because of it. A diff over half the profile's window is named, not shown. The diff rides on a request that compaction measured without it, so that one request can exceed `compact_at` by the diff; the next one compacts. A second look that ends `stuck` or at a limit without changing anything hands in what passed, and `why:` says so. The `recheck:` line says after which turn it was asked, how many characters of reasoning came back in the reply to it, and which files it changed, up to the reviewer's first call if one follows.

**Reviewer.** After a hand-in passes its checks and its second look, one request goes to the session's profile: the `REVIEWER` prompt, then the task (with the lead's defects in a round a reject started), `DSK.md`, the attached files, the diff, and the whole text of each changed file that is not new, while the message fits the profile's window at 3 characters a token. It has no tools and none of the worker's conversation, and its thinking effort is `reviewer_effort`. The reply must be one JSON object of findings. `dsk` keeps a finding only when its severity is known, its path is a file of the change, every field is filled in and its quote is in that file, compared with whitespace collapsed. It finds the line itself, drops repeats, findings whose own fix is no fix, and anything past the eighth, and from a reply cut off at `reviewer_tokens` or `reviewer_seconds` takes each finding that arrived whole. Blocker and major findings go back to the worker as a failed check does; minor ones are only reported. A later call sees the findings sent before and the author's answer from `done()`. A round has at most `reviewer_calls` calls, so the fix for the last call's findings is checked by the checks alone. A review that fails (an HTTP error, a cut-off reply with no whole finding, a reply that is not JSON) is recorded, and the hand-in goes ahead.

The call is a `reviewer` record with its own tokens, never `msg`, `req` or `usage`, so it neither breaks the worker's cached series nor counts toward `run_tokens`. Its whole reply is kept as `reviewer.N.json` in the session directory. The findings the worker is fixing stay in its first message through compaction, under `## The reviewer's findings`. The `review:` line counts each call's findings by severity, the dropped ones and the seconds, and how many quotes of the findings sent back are still in the code at the stop. The review packet lists each finding on a `finding:` line. The findings are the reviewer's claims, like `summary`; the counts are measured.

## State

State lives in `~/.local/state/dsk/<id>/`: the log, full turn outputs, the answer, the worktree and a lock. An id is four hex characters; once eight in a row are taken it grows to six, then to eight.

Nothing deletes a session by itself. `dsk prune` deletes the settled ones (`accepted`, `dropped`, `done`) that nothing was written to for `--days` (default `keep_days` in the config, else 30), `--dry-run` says what would go, and `"keep_days": N` in the config makes `dsk run` do the same once a day. A session that waits for a decision (`review`, `question`, `stuck`, `limit`, `error`) is never deleted, however old: it holds work nobody has judged, and its worktree. `dsk prune` names each one on a `kept:` line; `dsk accept` or `dsk reject ID --drop` settles it. The rule is `prunable()` in `lib/prune.ts`, with its laws proven.

## Stats

Every log record carries `at`, the time it was written. `dsk stats` reads the logs back: sessions by outcome; turns by kind (`read`, `write`, `run`, `stop`, `failed:<why>`); how many read turns came before the first change; how many turns had their output cut; reply sizes; tokens and cost; rejected rounds; and per profile the turns, tokens, failovers away and seconds per turn. `--sessions` adds a line per session and `--json` gives each session's numbers. A log from before timestamps existed gives no durations.

## Progress

`dsk status --json` prints `{"jobs": [...]}`, newest first, one object per session created in the last day on any project. Each is read off the session's log, so a run in flight shows where it is: `status`, and while running `phase` (`model` while it waits for a reply, `script`, `checks`), `doing` (the shell command or check in flight) and `act` (the last action the turn finished); `turn` of `max_turns` in the current round and `turns` overall; `in`, `out` and `cached` (the cached share of the input tokens, or null); `cost` in dollars, or null when a profile it used has no `price`; `failover` (the profile it left and why, such as `coralbricks 429`); `note` (the question, or why it stopped), `changed`, `brief`, `profile`, `owner`, `root`, `worktree`, and `created` and `active` in epoch seconds. What it read of a log is kept in `~/.local/state/dsk/status.json` and used again until that log moves, so a reading costs the same however many sessions the day holds: about 0.07 s, most of it Node starting.
