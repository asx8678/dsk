# What differs from the build prompt

Measured on 2026-11-11 with `deepseek-flash` on the official API and `deepseek-v4.1-flash` on a third-party gateway.

- **One `run_code` tool instead of plain-chat replies with `<file>` blocks.** In plain chat the model wrote its own tool-call markup or empty file blocks: 11 of 70 turns failed on the gateway and 5 of 46 on the official API, and one empty block wiped an in-scope file. With the tool, the last acceptance run (18 runs, each with unique content) had 1 failed turn in 60, a script the gate refused, and the 36-scenario trial batch had 1 in 132. A `files` argument was tried and dropped, because the model garbled it whenever it used it; files are written with `write()` and a raw triple-quoted string.
- **The cached share is at or just below the 0.9 target.** From turn 3 on, over three runs of the bench, it was 0.85 to 0.92 for code tasks on the official API (0.83 to 0.90 on the gateway) and 0.80 to 0.83 for web research (0.83 to 0.86 on the gateway). Every request does hit the whole of the previous one. What misses is what the last turn appended, and in a session of 2 to 4 turns that is a large part of a small prompt. Identical runs hit each other's cache entries and look better, which is why `tests/live.py` makes every run unique.
- **Thinking off is sent as both `thinking: disabled` and `reasoning_effort: "none"`,** because the gateway honours only the second. With `--effort` on, the forced call is not available, so `tool_choice` is `auto`, and the model's reasoning is sent back each turn as the API requires.
- **`max_tokens` follows the effort:** 16,000 with thinking off, then 32,000, 64,000 and 128,000.
- **System prompt:** rewritten around the tool, plus one sentence telling the worker to call `done()` in the script that runs the checks. That sentence took the median from 4 turns to 3.
- **One drafted rule was reworded.** "Re-read files instead of trusting old output or the attached copies" made workers read attached files and `DSK.md` again at once. It now says the attached files are current when the task starts and need no second read until something changes them. With `DSK.md` labelled as attached, redundant re-reads fell from 37 to 7 per 44 trial runs; total turns did not change beyond noise.
- **The scope gate runs after every script, not only at `done()`,** and undoes only what that script changed. As first built it undid every out-of-scope change since the start of the run, which deleted or restored files that someone else touched meanwhile. The change set, the review diff and `--drop` are limited to the worker's files for the same reason.
- **Compaction keeps small attached files and ends with a reminder about the large ones it dropped.** As specified, it dropped every attached file, and the worker then carried on from memory and invented what the file had said. Measured on a six-step task whose rules were in an attached file:
  - With a 400-character file and compaction forced at 2,000 tokens, 0 of 4 runs finished, with your original rule wording as much as with mine. Keeping the file: 4 of 4.
  - With a file of over 100,000 characters and one compaction at the configured thresholds, 5 of 6 finished, but only after a failed check sent the worker back to the file four turns later. With the reminder: 4 of 4, and the file is read again on the next turn.
  - Not tested: repeated compaction with a large file since the reminder was added (2 of 12 finished before it), and files between those two sizes. The 4,000-character limit is a choice, not a measured optimum.
  - Since 0.6.2, larger files also stay, in the order attached, while the compacted messages fit in half of `compact_at`, counted at 3 characters a token. The median is 3.24, measured on 487 first requests.
    - **Before:** of the 205 compactions logged from 2026-11-11 to 11-15, 139 dropped an attachment, and about 200 turns re-read one within six turns.
    - **The shipped code, replayed on all 221 compactions logged by 11-15:** on 48k profiles it keeps every large file in 77 of the 112 compactions that had one, and some of them in 19 more. On 24k profiles it keeps every one in 4 of 33, and some in 12. None goes past half the window. The 67 compactions with neither a reject nor a large file give the same bytes as before.
- **A reject's defects survive compaction (0.6.2).** The rebuilt first message held only the brief or the last `continue` task. A reject sent more than two turns before a compaction vanished, and the worker went back to the original brief with a fresh turn budget.
  - **Measured:** in the logs of 2026-11-12 to 11-15, 17 of the 22 reject rounds that compacted lost the list, and one of those rounds was accepted with a listed defect unfixed.
  - **Since then:** the reject's text follows the task under `## The lead's review`. `reject --max-turns N` caps that round alone. The `caution:` line of such a round counts the checks that passed when the previous round stopped.
- **Replies are streamed (0.6.3).** Without a stream, a gateway that hears nothing from its upstream for about 125 seconds gives up with HTTP 524, and a long thinking reply needs more than that.
  - **Before:** 37 524s in the 504 sessions logged by 2026-11-15: 1 in 42 turns at effort `max`, 1 in 245 at `high`, 1 in 850 without thinking. Each cost 125 seconds and a failover onto a cold cache, and 4 ended their run.
  - **Measured with streaming:** all five configured providers stream, report usage and cached tokens at the end, and send `[DONE]`. A 16,000-token reply streamed for 249 seconds through zro and a 32,000-token one for 202 seconds through opendesign, with no 524; the longest gap between events was 1.3 seconds and the first data came within 2.6.
- **A failover compacts for the profile it moves to (0.6.3).** A failover starts a series with no usage record, so compaction never looked: one run moved from a profile that compacts at 48k to one that compacts at 24k and sent it 37k.
- **Scripts and checks run in a macOS sandbox (0.7.0),** after the write-only seatbelt profile of DeepSeek Harness (`packages/sandbox/sandbox-local/src/profiles.ts`), with its lesson from postmortem 0004: whether the sandbox applies is tried once at the start, never guessed from a command's output. Before it, a worker's `sh()` could write anywhere you can and read dsk's own key file. Checks are inside it too, because they run code the worker wrote.
- **A second look and an independent reviewer (0.8.0), both off by default.** Measured by replaying logged hand-ins through zro, one reply each: the 23 that the lead rejected after their checks had passed (102 numbered defects), and 22 accepted at the first review, drawn at random from the same projects with thinking on.
  - **Second look:** without the diff, the first reply read or ran something again in 33 of 45 hand-ins; with the diff attached, as shipped, in 16. The reply edited a file of the hand-in in 10 of the 23 rejected ones and in 8 of the 22 accepted ones. Read by hand against the lead's lists, those 10 replies fixed 6 of the 102 defects outright and 2 in part; one reject, of a single defect, would not have been needed. Nobody has checked whether the 8 edits to accepted hand-ins helped or hurt. Median 84 s, 90th percentile 259 s, at effort max. A model judge was tried for the count and dropped: at effort off it quoted the lead's own list as the worker's evidence.
  - **Reviewer:** with thinking on (max, high or low) every call was still reasoning after 600 s, 100,000 to 129,000 characters of it, with no answer. Without thinking it answered in 29 s at the median. With the shipped prompt, 6 of 45 calls looped to the 16,000-token limit; with a first prompt that asked for every defect, 12 of 14 did, one listing 186 findings at 8 places. Hence the 4,000-token cap, at most 8 findings, and repeats dropped. Of 6 blocker and major findings on accepted hand-ins read in full, 2 withdrew themselves in their own text ("this is not a blocker", fix "n/a"), 1 called code uncompilable that had passed `go build ./...` in that run's checks, and 3 were debatable; so a finding whose fix is no fix is dropped too. With all these rules, its findings fell within three lines of 5 of the 40 lead defects that name a file and line (4 as blocker or major), and it raised a blocker or major on 17 of the 22 accepted hand-ins, 46 in all. It would send most hand-ins back: leave it off until it does better.
  - **Not measured:** whether either one saves a reject over a whole run rather than one reply, and what they cost in turns on real runs. One live run, a 19-line module at effort max, took two more turns for the second look: a probe of 5,800 output tokens, then the same `done()` with its summary reworded, which is not the same script, so it ran and the checks ran again. Its review took 0.7 s and found nothing.
- **Git-ignored output, a continued scout's turn limit and the plugin's key file (0.8.1),** found on 2026-11-15 by checking `skill/SKILL.md` against the code statement by statement: about 110 statements, 5 of them wrong or half wrong.
  - **Ignored output:** the change set is built from `git add -A` trees, so a file git ignores is in no diff. A worktree run whose only product was `out/hello.txt`, with `out/` ignored, ended `done` with its check passing, and the file went with the worktree. In place the file stayed, but the run still ended `done` and nobody reviewed it. Now a run that wrote such a file with `write()` or `edit()` stops as `review` with an `ignored:` line, and a worktree run refuses an `--allow` that names ignored paths. What a shell command writes to an ignored path is still listed nowhere.
  - **Turn limit:** a read-only run continued with `--allow` kept its 12 turns. It now gets the 30 of a writing run, unless `--max-turns` says otherwise.
  - **Key file:** the sandbox hid `~/.config/dsk` but not `options.json` in the plugin's data folder, where the form's keys are. Tried under the profile a session gets, that file could be read. It is hidden now, with the `.new` copy written beside it.
  - **Search key:** `--web` without the search key printed the text of a missing provider key, which reads as "dsk has no provider". It has its own message now.
- **After a rejected round, `show --review` prints only what changed since the last review.**
- **A 429 that survives the retries also fails over,** like a repeated 5xx. So does a network failure.
- **`python3 -I` discards `PYTHONHASHSEED`,** so the seed is pinned for `sh()` and checks but not for the script process itself.
- **In a git repository the working directory is the repository root.**
- **Size:** `dsk.py` has 1,520 lines, over the 1,000-line target and, since the key file, `max_sessions`, `status --json`, `configure`, profile `headers` and provider pauses were added, over the 1,300-line limit too (48 lines are longer than 120 characters). By your rule the next step is to cut a feature: the candidates are `doctor` (about 55 lines), the raw `search` and `fetch` commands (12), and the time and token limits (6).
